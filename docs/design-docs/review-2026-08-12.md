## Fixed this session

**Live history was never restored, and cross-channel sends never reached it.**
`channel.rs` created history as `Vec::new()` with no hydration, and
`send_message_to_another_channel` wrote only through `ConversationLogger` (its
comment said "so it appears in future transcripts" — the durable view, not the
runtime one). Two independent consequences: every channel started blank after a
restart, and a proactive send into a *resident* channel was invisible to that
channel's next turn.

Evidence, both from the telegram channel:

| Seq | Time (UTC) | What happened |
|---|---|---|
| 24 | 02:19:40 | SpaceUI survey delivered by cross-channel send |
| 25 | 02:41:20 | "why did you send me that?" |
| 26 | 02:41:47 | agent: "this Telegram history has no preceding message saved" |
| 27 | 04:10:00 | setup-gaps message delivered by cross-channel send |
| 30 | 04:11:24 | agent answers with no referent, 74 seconds later |

The 04:10 case would have been fixed by restore alone (channel was cold after a
restart). The 02:19 case would not — that channel was already warm, so there was
no activation to hydrate on, and only live injection covers it. Both fixes are
needed; neither subsumes the other.

Fixes in `6b6420b2` and `e8aa1992`:

- `ChannelRunner::hydrate_history()` at the top of `run()`. Under chronicle mode
  it loads from the newest checkpoint's `end_boundary()` so the chronicle view
  and live history don't both represent the same span; under rolling it takes the
  newest slice via `newest_messages_after` (`messages_after` would have returned
  the *oldest* N — that query is `ORDER BY seq ASC LIMIT`). Capped at
  `HYDRATE_MESSAGE_LIMIT = 200`, then calls `fence.record_turn(live_len, seq)`.
- `ChannelState::inject_agent_message()`, called by the send tool via
  `deps.process_control_registry.channel_handle()`. It appends under the lock and
  then calls `note_head_mutation()` — necessary because an in-flight chronicle cut
  holds a fence snapshot and would otherwise trim against stale state. This is why
  `history_fence` moved onto `ChannelState`.
- **Self-exiting channels are excluded from restore.** Cron and autonomy runs are
  fresh single-shot sessions whose durable rows are their own wake prompts;
  without the gate, every autonomy run would load ~158 near-identical briefings.
  Caught before deploy, verified after: autonomy started at 05:23:34 with no
  restore line.

## Open — root cause identified, not fixed

**The autonomy channel cannot complete an LLM call.** 36 failures on 2026-08-12,
87 on 2026-08-11, and every single one is `channel_id=autonomy` — zero on any
other channel. Full error:

> expected text-bearing message content (output_text/text/summary/refusal/content)
> or function_call output items; received output types: message

A message item comes back with nothing the parser can extract. The autonomy
prompt tells the model *"nothing you say is delivered to anyone; work happens
through tools only"* — the model complies by returning an empty message, and the
parser treats that as an unsupported response rather than a legitimately empty
completion. Consistent with runs that end on `AUTONOMY_FALLBACK_SUMMARY` because
`autonomy_complete` was never called.

Fix direction: treat a message item with no text-bearing content as an empty
completion instead of an error, in the Responses API parser
(`src/llm/model.rs`, same area as the `response.failed` handling). Blast radius
is every provider and channel, so it needs care not to swallow genuinely
malformed responses.

**This blocks chronicle verification.** Checkpoints are still at 0. Autonomy is
the only channel taking scheduled turns; its call fails before
`maybe_maintain_context` runs, so the chronicler never gets invoked despite 158
uncovered messages against a threshold of 40. Chronicle mode may be working and
simply never reached. Telegram (32 uncovered, 8 short of 40) takes turns through
a path this bug doesn't affect and is the clean way to test.

## Open — diagnosed, designed, unimplemented

**Autonomy runs close before their own work finishes.** Run `a310eed2` called
`autonomy_complete` at 02:17:30; the worker it spawned started at 02:17:33 and
returned at 02:19:13, and the message it produced went to Telegram at 02:19:40 —
inside no run window at all. `autonomy_complete` is a model-invoked terminal
contract with nothing checking for outstanding children, so the run summary
described a different project entirely and the outbound message has no ledger
entry. Designed in [autonomous-action-audit.md](autonomous-action-audit.md),
phases 1–5, none implemented.

**The autonomy channel persists only wake injections.** All 158 rows for
`channel_id = 'autonomy'` are the same injected briefing — no assistant turns, no
delegate-result injections. The agent's self-directed reasoning is unrecoverable,
and the chronicler can never cover it.

**The task loop is in a stable deadlock.** `level = "act"` permits task creation,
but with `tasks: 0` and `goals: 0` the `instance_is_empty` branch of
`autonomy_channel.md.j2` fires and says *"Do not invent tasks to look busy."* So
no tasks get created, so the instance stays empty. Its designed output is "the one
question worth asking," written into `autonomy_runs.summary` — and the ask surface
(`pending_questions`, `src/questions.rs`) needs a channel with a human plus a
`message_ref`, while the autonomy hard rules forbid messaging users. The loop has
asked the same question at least three times into a database column. **Exit: give
it one goal.**

**Portal renders the agent as `main` rather than `Orion`.** Data is clean —
`sender_name` is `'Orion'` on all twelve assistant rows including the ones
displaying as `main`. Purely a rendering regression; prime suspect is the 712-line
`PortalTimeline.tsx` rewrite in `e980bb65`.
