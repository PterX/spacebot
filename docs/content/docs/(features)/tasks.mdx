# Tasks

Tasks are the durable unit of work in Spacebot. They live in the instance-wide task store, so an agent can own a task, another agent can execute it, and an operator can inspect the same record from the dashboard, API, or CLI.

A task has a title, a markdown specification, priority, status, owner, optional assignee, subtasks, goal links, and execution metadata. The description is written for the process doing the work. It should include requirements, constraints, affected paths, and acceptance criteria.

## Lifecycle

| Status | Meaning |
| --- | --- |
| `pending_approval` | Proposed work awaiting operator approval. |
| `backlog` | Captured work that is not ready to run. |
| `ready` | Approved and eligible for autonomous execution when dependencies allow it. |
| `in_progress` | An agent or worker is currently acting on the task. |
| `done` | Work completed. |
| `failed` | The most recent execution reached a terminal failure. |

Agent tools and autonomous execution enforce normal transitions. The UI, CLI, and operator API can directly reconcile a task when work completed outside Spacebot. Marking a task done directly records completion without fabricating an approval.

## Execution Plans

An execution plan makes the environment for a task explicit before a worker starts:

- **Worker type**: built-in worker or OpenCode.
- **Project and repository**: the registered codebase that owns the work.
- **Worktree mode**: run in the root checkout, use an existing worktree, or create a dedicated worktree.
- **Required skills**: mandatory instructions injected into the worker context.

Task fields override project defaults. A plan can be incomplete while a task is being refined. An executing agent resolves the final worker configuration when it claims ready work.

## Dependencies

Tasks can depend on other tasks through two edge types:

| Edge | Readiness rule |
| --- | --- |
| `gate` | The dependency must be done before this task can run. |
| `stack` | The dependency must have a branch or worktree available, or be done. Use this for stacked implementation work. |

Ready tasks with unsatisfied edges are blocked. The task list exposes the blocking task numbers and the state of every dependency edge.

## Autonomy

An autonomy run receives queued wakes, active goals, task state, and its recent run history. At `suggest`, it can propose and enrich work for approval. At `act`, it can select ready, unblocked tasks and delegate their execution.

The task record carries recovery state. If a process exits mid-run, the next wake reads the durable task and run history instead of relying on a transient conversation.

See [Autonomy](/docs/autonomy) for levels, wakes, and run history.

## Creation

Tasks can be created through conversation, the dashboard, the API, and CLI. Conversational task work goes through a branch, which turns the user request into a durable specification and updates it as scope changes.

Tasks created by autonomous deliberation default to `pending_approval`. Operator-created tasks normally begin in `backlog` and move to `ready` when the plan is sufficiently defined.

## Operator Workflows

The CLI covers the common task lifecycle:

```bash
spacebot task list --status pending_approval
spacebot task create "Review deployment plan" --owner main --priority high
spacebot task approve 42 --approved-by jamie
spacebot task execute 42
spacebot task assign 42 engineering
spacebot task update 42 --status done
```

The API accepts the execution plan and dependency edges on task create or update. Use `depends_on` entries with a task number and optional `gate` or `stack` kind. The task list supports owner, assignee, status, priority, and creator filters.

## Interface

The task list shows status, priority, owner, assignee, plan details, dependency state, subtask progress, linked research, and worker activity. The detail view renders the specification, dependencies, execution plan, and action history.

Task changes are emitted over SSE so the dashboard updates without polling.

## APIs and Tools

The REST API supports listing, creating, updating, approving, and reconciling tasks. Branches use `task_create`, `task_list`, and `task_update` to manage work during a conversation. Workers can report scoped progress without granting them unrestricted control over task lifecycle fields.
